When Saint Demetrios Greek Orthodox Church in Seattle needed to bring the Divine Liturgy to parishioners who couldn't be there in person, they didn't hire an AV company.

They had a parishioner who happened to be a software engineer — one who saw every challenge as an architecture problem waiting to be solved. What started as "can we livestream the Liturgy?" became a full-stack parish AV platform: automated scheduling, cloud streaming, sermon post-production, robotic cameras, lobby displays, and centralized monitoring — all built from scratch, one commit at a time.

This is that story.

# YT Azure Streamer

Infrastructure that sleeps when the stream does.

A parameterized Azure deployment that provisions a streaming VM with a single ARM template command. The VM plays a recorded service from Blob Storage to YouTube Live with ffmpeg, wakes up two minutes before each scheduled stream, and deallocates afterward so nothing runs — or bills for compute — while idle.

  • One-command deploy: ARM template plus interactive deploy.sh / deploy.ps1 with name, region, and SKU pre-flight checks
  • No secrets on disk — stream key and credentials live in Key Vault, read via managed identity
  • Azure Automation starts and stops the VM on a weekly schedule; role assignments are wired in the template
  • Recordings mounted from Blob Storage with blobfuse2; ffmpeg settings tuned for stable YouTube ingest
  • Password-protected web UI for playlists, schedules, logs, and monitoring, served by Caddy with automatic TLS

# Sermon Pipeline

After the Liturgy, the work is just beginning.

A post-production pipeline for church broadcast recordings. It finds the sermon inside a multi-hour live stream, cuts it out, writes a title and description, and prepares YouTube Shorts — built as an MCP server driven by an AI agent, with skill files that encode extensive Orthodox theology and terminology rules so the output is always reverent and tradition-accurate.

  • MCP server exposing deterministic tools for boundary detection, segment download, Shorts extraction, and validation
  • Sermon boundaries from the transcript, with an audio silence-gap fallback and side-by-side redetection
  • Per-sermon directory packages instead of monolithic JSON, plus append-only indexes that can be regenerated
  • Layered by how deterministic the work is: scripts, then tools, then skills, then the agent — which keeps runs cheap and predictable
  • Fetches the weekly Sunday School lesson with headless Chromium and works it into the liturgy description
Python MCP Playwright yt-dlp FFmpeg VS Code Agents

# Church Monitoring

Because even the best systems need oversight.

A lightweight centralized monitoring and control system for church AV infrastructure. Clients collect system metrics via cron; the server fetches on demand with parallel queries and caching. The HTTPS dashboard shows device health and lets an operator act on it — restart a service, switch a TV's input, or start a standby timer — all secured with mutual TLS and token-based enrollment.

  • Pull-based architecture: server fetches from clients on demand, in parallel, with 30-second response caching
  • Mutual TLS with token-based device enrollment
  • Host actions from the dashboard: restart services, CEC TV power and input, standby countdown
  • Connectivity checks for devices that run no client — cameras, encoders, AV gear
  • Remote screenshot capture via X11 display grab
  • ntfy alerts on errors; per-role AppArmor profiles laid down by the church-service-installer

# Ambient Streamer

A stream that never blinks.

A headless, multi-channel, 24/7 streaming engine. Each channel pairs a Liquidsoap audio engine with an FFmpeg compositor that renders a color-adaptive slideshow and live audio visualization, publishes to YouTube over RTMP, and exposes a low-resolution HLS preview. One rule shaped every decision: a 24/7 stream must never restart FFmpeg — so every live-editable feature routes around it.

0.996×realtime speed
0dropped frames
~1.4 smake-before-break restart
  • Audio lives in a separate Liquidsoap process behind an Icecast fallback mount — restarting it measured a 0 s gap, versus an 18 s stall with direct output
  • Images arrive on a pipe, colors change over ZMQ, and visualizations switch with streamselect — all on the running filtergraph
  • FastAPI control plane renders per-channel Compose files and runs the supervisor, watchdog, scheduler, and live SSE updates
  • Encoder profiles for libx264, NVENC, and QSV, with automatic fallback when a GPU's session cap is reached
  • Armed soundboard overlays mix in over the music without interrupting the stream; the operator UI is plain JS with no build step
Python FastAPI Docker Compose FFmpeg Liquidsoap Icecast MediaMTX

# Fitness Instructor Music

Class music that keeps teaching when the Wi-Fi doesn't.

An offline-first progressive web app for running a fitness class. One routine holds the walk-in music, the cued set list, filler between songs, and the walk-out — it saves to the device first, syncs to Azure when it can, and plays prepared audio with no connection at all. Routines are shared with a small group through owner, editor, and player roles.

  • Local-first saves: durable in IndexedDB, queued for cloud sync, and never force-overwritten when revisions conflict
  • Blob-backed API with ETag-conditional locks, immutable published revisions, CSRF protection, and throttled sign-in
  • Cue and exercise clocks run on audio time, not UI interval ticks, so timing doesn't drift
  • BS.1770 / EBU R128 loudness measurement and BPM estimates, applied only after review
  • Service-worker offline shell, drag-to-reorder editing, undo/redo, and Excel and PDF exports
TypeScript Vite Web Audio Service Worker Azure Functions Playwright
